## Context

Phase 1 (catalog + resolution) and Phase 2 (provisioning) of [`saas-multi-account-architecture.md`](saas-multi-account-architecture.md) are **done and smoke-verified**: per-account DBs are provisioned, the subdomain → account → tenant-DB resolution works, and unknown subdomains fail closed (404). The account-aware tenant connection is applied in `KrakenDbContext.OnConfiguring` via `IAccountContext.ResolveTenantConnectionString()` (multi-account override; throws if unresolved = fail closed; null = single-instance no-override).

**What Phase 3 fixes:** that mechanism only works for consumers running in a true **request scope**. The existing single-tenant app has consumers that open a tenant `DbContext` **outside** a resolved-account request scope, so tenant **pages** currently `500` in multi-account mode. Phase 3 makes the rest of the app account-aware so the tenant UI is navigable and background work runs per-account.

Enable multi-account in dev with: `MultiAccount__Enabled=true`, `MultiAccount__BaseDomain=localhost`, `ConnectionStrings__Catalog=…`, `ConnectionStrings__ShardAdmin=…`, and `ASPNETCORE_URLS=http://localhost:5080` (http-only so `UseHttpsRedirection` no-ops). Demo accounts `acme` / `globex` are auto-provisioned by `ControlPlaneDevSeed`.

## Tasks (ordered by dependency / value)

### P3-1 — Blazor circuit + prerender account-carry  ·  **gating, do first**
**Problem.** Blazor's interactive **circuit** runs in a DI scope that is *not* the HTTP request scope; the account `AccountResolutionMiddleware` pins onto the request-scoped `IAccountContext` is invisible to components/services resolved in the circuit (and to some prerender paths). Symptom: `Login.OnInitializedAsync` → `FeatureFlagService` throws *"No business account has been resolved"* → tenant pages `500`.
**Approach.** Add an `AccountCircuitHandler : CircuitHandler` that, on circuit creation, resolves the account from the establishing connection's **host** (the subdomain is stable for the circuit's lifetime — a circuit is per-origin) via `IAccountResolver`, and re-applies it onto the circuit scope's `HttpAccountContext` on each render/activity. **Mirror the existing Space circuit-carry** (`SpaceContextBoundary` / the Space `CircuitHandler`) — same pattern one level up. Verify prerender (request scope) also sees the account.
**Files.** New `src/KrakenDeploy.Server/Accounts/AccountCircuitHandler.cs`; register in `Program.cs` (multi-account only); reference the Space circuit-carry impl.
**Acceptance.** `acme.localhost:5080/login` renders the sign-in form; signing in authenticates against `kraken_acct_acme`; `globex.localhost` is independent; no "no account" errors on page loads.

### P3-2 — Per-account background work + clear stale Hangfire schedules
**Problem.** (a) Recurring jobs assume a single DB and fire with no account → throw. (b) They were registered in an earlier run and **Hangfire persists recurring jobs in its store**, so they keep firing even though `Program.cs` now skips re-registration in multi-account mode. (c) The `DeploymentWorker` / `RunbookRunWorker` channel readers process queued items without an account.
**Approach.** (a) On startup in multi-account, `RecurringJob.RemoveIfExists(...)` for every single-tenant job id (clean the stale store). (b) Re-model recurring jobs as a **per-account fan-out**: one scheduler enumerates active accounts from the catalog and runs each job's body inside a `WithAccount(...)` scope (same mechanism as `TenantInitializer` / `FleetMigrationOrchestrator`). (c) Make the in-process dispatch channel carry `accountId` (or resolve the owning account before `WithAccount`) so the worker binds to the right tenant DB.
**Files.** `HangfireJobRegistrar`, `src/KrakenDeploy.Server.Data/Jobs/*` (AuditRetention, AgentLastSeenOffline, RegistrationTokenExpiry, ScheduledDeploymentDispatch, StepTemplateCatalogPoll, StepPackageCatalogPoll, Backup, SubscriptionPoller, EmailDigestFlush, AiCallLogRetention), `DeploymentWorker`, `RunbookRunWorker`, the dispatch `Channel<Guid>`.
**Acceptance.** No "no account" errors in the log at idle; a recurring job processes every active account; a queued deployment runs against its own tenant DB.

### P3-3 — Hangfire storage / topology decision (multi-account)  ·  **DONE (2026-06-26)**
**Resolved.** In multi-account the Hangfire job store points at the **catalog / control-plane DB** (`GetConnectionString("Catalog")`), not the shared base `KrakenDb`; single-instance keeps `KrakenDb`. Job *bodies* stay per-account via the `PerAccountRecurringJobRunner` fan-out (`WithAccount`). Verified: a multi-account boot creates Hangfire's schema in `krakendeploy_catalog` (12 tables). `Program.cs` Hangfire `UseNpgsqlConnection(hangfireConnectionString)`.
**Dashboard isolation (2026-06-26).** Because the store is now one shared control-plane store, the `/hangfire` dashboard would otherwise show platform-wide (cross-account) job state to any per-account System Administrator (`AdministerSystem` is resolved from the tenant DB). `HangfireDashboardAuthFilter` now **denies the dashboard on any tenant subdomain** in multi-account (the subdomain gate runs before the auth/permission check), so it is control-plane-host-only — effectively closed until a control-plane admin surface exists (fail-safe). Single-instance unchanged. Verified: `acme`/`globex`/apex `…/hangfire` → 401; tenant `/login` → 200.
**Problem (original).** Hangfire used the single `KrakenDb` connection for its job store. Under DB-per-account there's no single tenant DB.
**Approach.** Decide + implement: **one control-plane Hangfire store** (recommended — jobs are control-plane fan-out per P3-2) vs. per-account schemas. Point Hangfire at the catalog/control-plane DB; keep job *bodies* per-account via `WithAccount`.
**Files.** `Program.cs` (Hangfire `UsePostgreSqlStorage` connection), config.
**Acceptance.** Hangfire dashboard + jobs run against the control-plane store; no tenant coupling in the scheduler.

### P3-4 — Control-plane vs tenant host split in the pipeline
**Problem.** Apex / control-plane hosts (`app.`, `signup.`, `auth.`, bare domain) currently pass through to the tenant Blazor app (which `500`s with no account), and `HostParser` treats `app.`/`signup.`/`auth.` as tenant subdomains → `404` (they aren't accounts).
**Approach.** Recognize reserved control-plane hosts in resolution and route them to a **control-plane surface** (even a placeholder landing for now), not the tenant pipeline / not fail-closed. Lays the groundwork for the signup/admin portal (Phase 4).
**Files.** `AccountResolutionMiddleware`, `HostParser` / `MultiAccountOptions` (reserved control-plane hosts), `Program.cs` host-based branch.
**Acceptance.** `app.localhost` / apex serve a control-plane response (not a tenant 500/404); tenant subdomains unaffected.

### P3-5 — Per-account caching for the cache services  ·  **optimization, after P3-1**
> **Leak fixed (2026-06-26):** `LicenseUsageCounter` was registered `AddSingleton` *unconditionally* (its four sibling cache services were scoped in multi-account; it was missed), so its process-wide 60s `(Targets, Users)` snapshot served one tenant's counts to another's license banner. Now `AddScoped` in multi-account (single-instance keeps Singleton), mirroring the siblings. The per-account-keyed `ConcurrentDictionary` cache below applies to all five services.
**Problem.** `FeatureFlagService`, `MaintenanceModeService`, `DeploymentFreezeService`, `PerformanceSettingsService` were made **Scoped** in multi-account mode (correct, but re-queries per request — no cross-request cache).
**Approach.** Restore caching keyed by `accountId` (singleton holding a `ConcurrentDictionary<Guid, …>` — **not** a plain `Dictionary`, see the scoped-cache-concurrency lesson), reading the current account from the scope. Optional; correctness already holds via Scoped.
**Files.** the four services in `src/KrakenDeploy.Server.Data/Services/`, their registration in `ServiceCollectionExtensions.cs`.
**Acceptance.** Single DB read per account per TTL window; no cross-tenant cache bleed; load test shows the regression from Scoped recovered.

### P3-6 — Audit & sweep remaining root-scope tenant-DB touches  ·  **sweep DONE**
**Problem.** Other singletons / hosted services / startup paths may open a tenant `DbContext` without an account (the fail-closed throw is the detector).
**Sweep result (2026-06-24).** Request, SSR, Blazor-circuit, and background **recurring-job** paths are clean — a full idle run + navigation produces **zero** "no account" errors. The only remaining root-scope tenant-DB touches are one cohesive surface: the **executor + agent-transport tier** (see P3-8). `LicenseService` is global/control-plane (license file, no tenant DB) → no change. `BackupScheduler`/`BackupJob` are per-tenant but only run on the backup schedule → covered by the P3-2 fan-out pattern when wired (low priority; backups per account).
**Inventory of remaining touches** (`src/KrakenDeploy.Server.Transport/`): `DeploymentWorker`, `RunbookRunWorker`, `DeploymentDiagnosisWorker` (in-process `Channel`/`RunbookRunChannel`/`DeploymentDiagnosisChannel` readers — each opens `KrakenDbContext` from a fresh scope); the step runners they call (`DeployReleaseStepRunner`, `ServerScriptStepRunner`); and the agent transport (`AgentHub`, `Grpc*Service`). All process work for a specific account but carry none. Because `WithAccount` is now `AsyncLocal`, the fix is to set the account **once at each entry point** (worker dequeue / hub connection) — the step runners and inner scopes inherit it.

### P3-8 — Executor & agent-transport account-awareness  ·  **server-side implemented + build/unit/smoke-verified; live-agent verification pending**
**Why separate.** This is the product's core execution path (deployments to government targets) and the agent link. It is higher-risk than the rest of Phase 3 and **cannot be end-to-end verified without a connected agent + a real deployment**, so it warrants its own focused, tested increment rather than a blind change.
**In-process channels — DONE (build-verified, not deployment-execution-verified).** The three channels now carry `TenantWorkItem(Guid AccountId, Guid Id)` (deployment dispatch `Channel<TenantWorkItem>`, `RunbookRunChannel`, `DeploymentDiagnosisChannel`). Writers (`DeploymentService`, `RunbookService`, `ScheduledDeploymentDispatchJob`, `DeploymentWorker` diagnosis enqueue) stamp the account from `IAccountContext.CurrentAccountId` (multi-account) or `Guid.Empty` (single-instance). `IAccountResolver.ResolveByIdAsync` added (catalog-by-id + cached). The three workers (`DeploymentWorker`, `RunbookRunWorker`, `DeploymentDiagnosisWorker`) resolve the id → `ResolvedAccount` and wrap processing in `WithAccount`; the step runners + inner scopes inherit via `AsyncLocal` (no per-runner change). `DeploymentWorker.FailAsync` reads the account from a per-dispatch `AsyncLocal<Guid>` to tag the diagnosis item. Full solution builds 0/0; idle smoke = 0 "no account" errors, request path intact. **NOT yet verified with a real deployment** (needs a connected agent), and actual execution is still gated by the agent transport below.
**Agent transport — RESOLVED (host-derived).** Agents connect over a reverse tunnel authenticated by `AgentJwt` (carries `targetId`, **no account**), so the server could not tell which account a connected agent belongs to. Decision: resolve it the **same way the web does** — the agent connects to its account subdomain and `AgentHub`/gRPC read the account from `Request.Host` (no token claim, no catalog index). See the **Design drafted** note below for the full rationale, the rejected alternatives, and the two prerequisite bugs; wire `AgentHub`/gRPC to `WithAccount` once those are in.

**Design drafted:** see [`design-agent-transport-account-awareness.md`](design-agent-transport-account-awareness.md) (v0.2). Decision: **host-derived account identity** — the agent connects to its account subdomain (`<sub>.<base>`) and the server resolves account from `Request.Host` via the existing `AccountResolutionMiddleware` → `CatalogAccountResolver.ResolveAsync(host)`, exactly as the web plane does. No new cross-tenant table; reuses existing resolution. (v0.1 recommended a control-plane `agent_registry`; reversed — its only edge, zero agent reconfiguration on conversion, is moot pre-production.) Edge `Host`-preservation verified against the Caddyfile (Caddy forwards `Host` by default; only new edge need is a wildcard site + DNS-01 cert, shared with the web). Composes with the later PoP enrollment redesign ([`design-agent-enrollment-cert-auth.md`](design-agent-enrollment-cert-auth.md)). Two prerequisite bugs verified in code and shippable standalone: (1) `TargetRegistrationService.ValidateAndConsumeTokenAsync` lacks `.IgnoreQueryFilters()` → non-Default-Space targets cannot enroll; (2) `AgentHub.OnConnectedAsync` fails open (registers before the DB lookup, not-found branch only logs — no `Context.Abort()`).
**IMPLEMENTED (server-side) — 2026-06-26.** Host-derived account identity is wired and build/unit/smoke-verified (NOT yet live-agent-verified):
- **Phase 0 (enrollment bug):** `ValidateAndConsumeTokenAsync` now uses `.IgnoreQueryFilters()` (`TargetRegistrationService.cs`). Regression test `ValidateAndConsume_finds_target_in_non_default_space` (`TargetRegistrationServiceTests.cs`) passes — non-Default-Space targets can enroll; full registration suite green (7/7, real Postgres).
- **Phase 2/3 (hub):** new `AgentAccountHubFilter` (`KrakenDeploy.Server.Transport`) — an `IHubFilter` added to `AgentHub` **only when `MultiAccount:Enabled`** — resolves the account from the connection host via `IAccountResolver`, caches it on `HubCallerContext.Items`, and `WithAccount`-wraps `OnConnectedAsync` / every `InvokeMethodAsync` / `OnDisconnectedAsync` (the disconnect wrap lets the deferred mark-offline task capture the account via `ExecutionContext`). `AgentHub.OnConnectedAsync` now validates the target **before** `registry.Add` and **aborts** an unknown target (was: log-and-stay-connected — fail-open). Single-instance installs never add the filter and run byte-identically (one behavior change in both modes: an agent whose target no longer exists is now aborted).
- **Phase 1 (enroll URL):** no change — the wizard already derives the agent `Server:Url` from `Nav.BaseUri` (`AddTargetWizardDialog.razor`), which **is** the operator's account subdomain in multi-account mode.
- **Phase 4 (gRPC):** no change — the three `Grpc*Service` classes create their `KrakenDbContext` inside the gRPC request scope where `IHttpContextAccessor.HttpContext` is non-null, so the middleware-resolved account flows via `HttpContext.Items` (the SignalR-hub `IHttpContextAccessor`-is-null problem does not apply to gRPC).

- **Phase 5 (dispatch cross-account guard) — DONE.** `IAgentConnectionRegistry` now records the connection's account at connect (`Add(connectionId, targetId, accountId)`; `GetAccountForTarget`), set by `AgentHub` from the filter-pinned `IAccountContext` (in-memory in both the single-server and HA-Postgres registries — node-local, no schema change). `DeploymentWorker` and `RunbookRunWorker` assert, before dispatching to a target's connection, that the connection's account equals the dispatch account (`_dispatchAccountId`); a mismatch is blocked (deployment: dropped like an offline target; runbook: failed) and logged at error. Defense-in-depth — structurally a mismatch cannot occur (globally-unique `targetId` validated against the connecting account's DB at connect) — but it now fails closed if an upstream invariant ever breaks. `AdhocDispatcher` is intentionally **not** guarded (it is a singleton on the interactive path; injecting `IAccountContext` would be a captive dependency, and the circuit sets the account via `SetResolved`, not the static `WithAccount` AsyncLocal — guarding it cleanly needs the account threaded into `DispatchAsync`, deferred). Verified: solution builds 0/0; AgentHub + Orchestrator + Registration suites 29/29, AdhocDispatcher 7/7 (real Postgres). (Also fixed a stale `OrchestratorE2ETests` assertion the prior channel-carry left untested — it compared a `TenantWorkItem` to a `Guid`.)

- **Connection-registry persistence REMOVED — DONE.** A shared-state audit (2026-06-26) found the `agent_connections` table was **never read** — `PostgresAgentConnectionRegistry` only wrote it; every read is node-local memory. So persistence (per-account *or* shared) was dead weight + a false HA promise (HA correctness rests on sticky-session routing, not the table). `PostgresAgentConnectionRegistry` was **deleted**; `InMemoryAgentConnectionRegistry` is used in all modes. Connection state is self-healing — a dropped agent reconnects and re-registers — so it needs no durability (contrast Hangfire, whose jobs must survive restart → P3-3). The in-memory registry still tracks the per-connection account, so the Phase 5 dispatch guard is unaffected. (This supersedes the earlier per-account-write change, which was correctly isolating something that shouldn't have been persisted at all.) A genuine cross-node registry is deferred until a SignalR backplane (Redis) exists. The `agent_connections` table (now unused, empty, UNLOGGED) can be dropped in a later migration.

**Remaining:**
- **Phase 6 (middleware tighten):** the `AccountResolutionMiddleware` apex pass-through is left as-is; the hub filter is the fail-closed backstop for `/hubs/agent` (apex host → resolver returns null → abort) and gRPC fails closed via the `KrakenDbContext` no-account throw. An explicit agent-path rejection in the middleware was not added.
- **Phase 7 (edge):** wildcard site (`*.{$DOMAIN}`) + DNS-01 wildcard cert — a deployment/ops change to the SaaS Caddy config (the on-prem reference Caddyfile stays single-host). Not done.
- **Live-agent verification:** the actual agent connect → `WithAccount` → deployment execution path needs a connected agent + a 2-account E2E. Not verifiable in-repo.

**Acceptance.** A scheduled deployment + a runbook run + an agent connection each execute against the correct tenant DB; zero "no account" errors under load with agents connected.
