# Authoring step packages

> Version: 1.1. Last updated: 2026-05-21. Status: Draft.

A *step package* is a versioned, signed `.kdeploy-step` archive that supplies
a custom step type to a KrakenDeploy installation. Authors get exactly the
same execution model the built-ins use — including the schema-driven UI, the
per-step version pin, the gRPC delivery to agents, and the catalog/UI/CLI
surfaces — by referencing one NuGet (`Kraken.SDK`) and following the
conventions below.

This guide covers:

1. [Scaffolding a new package](#scaffolding-a-new-package)
2. [The manifest](#the-manifest)
3. [The `IStepHandler` contract](#the-istephandler-contract)

## Scaffolding a new package

```pwsh
dotnet new install Kraken.SDK.Templates
dotnet new krakenstep -n MyCompany.MyStep `
    --stepTypeId "MyCompany.DeployToS3" `
    --packageId  "mycompany.deploy-s3"
cd MyCompany.MyStep
dotnet build
```

Output: `bin/Debug/net10.0/mycompany.deploy-s3-1.0.0.kdeploy-step`. That file
is what you upload, attach to a GitHub Release, or hand-deliver to the server
in an air-gapped install.

The scaffolded layout:

```
MyCompany.MyStep/
├── MyCompany.MyStep.csproj    # References Kraken.SDK + carries the pack target
├── SampleStepHandler.cs       # Your IStepHandler implementation
├── ui-schema.json             # Form schema the editor renders
└── README.md                  # Project-local pointers
```

## The manifest

`manifest.json` lives at the zip root. It's generated by the MSBuild pack
target from the `.csproj` metadata properties — you don't write it by hand.
The shipped fields:

| Field | Required | Example | Notes |
|---|---|---|---|
| `id` | yes | `"mycompany.deploy-s3"` | Lower-case, dotted. Same as the schema id; multiple versions coexist under one id. |
| `version` | yes | `"1.0.0"` | Semver. Used by the agent loader's cache key and the catalog's upsert. |
| `displayName` | yes | `"Deploy to S3"` | Shown in the editor's step-type picker. |
| `targetFramework` | yes | `"net10.0"` | The TFM the executor DLL was built against. |
| `stepTypes` | yes | `["MyCompany.DeployToS3"]` | Step type strings your handler's `CanHandle` returns `true` for. A single package may claim multiple step types — `kraken.script` handles both `Kraken.Script` and `Octopus.Script`. |
| `executorAssembly` | yes | `"MyCompany.MyStep.dll"` | DLL inside the `executor/` folder. |
| `executorTypeName` | yes | `"MyCompany.MyStep.SampleStepHandler"` | Fully-qualified name of the `IStepHandler` class. |
| `signedBy` | optional | `"mycompany"` | Identifier of the signing key. Informational in v1. |
| `signature` | populated by signing | base64 | RSA-SHA256 over the canonical input — see [Signing setup](#signing-setup). |
| `description`, `author`, `homepage`, `minKrakenAgent` | optional | | Surfaced in the catalog UI. |

The pack target emits these from the `.csproj`'s `KrakenStepPackage*`
properties. To change values, edit the project file (not the generated
`manifest.json`).

## The `IStepHandler` contract

```csharp
public interface IStepHandler
{
    bool CanHandle(string stepType);
    bool RequiresPackage { get; }
    Task<bool> HandleAsync(StepHandlerContext context, CancellationToken ct);
}
```

Lifecycle: **per-step-execution**. The agent's `StepPackageLoader` calls
`Activator.CreateInstance(handlerType)` for each step. The type must have a
public parameterless constructor. Don't cache state across calls — multiple
deployments run concurrently, each with its own handler instance.

`HandleAsync` receives a `StepHandlerContext` with everything the agent
knows about the step:

| Field | Purpose |
|---|---|
| `Plan` | Full `DeploymentPlan` — environment name, variables (Octostache-substituted server-side), all steps. |
| `Step` | `DeploymentStepPlan` for this step — name, config bag, package version. |
| `ExtractDir` | On-disk path where the step's primary package was extracted. Empty when `RequiresPackage == false`. |
| `ArtifactsDir` | Write files here; the agent uploads them to the server after the step. Exposed to scripts as `KRAKEN_ARTIFACTS_PATH`. |
| `LogAsync` | `(level, message) => Task` — append a log line. `level` is `"info"`/`"warning"`/`"error"`. |
| `ReferencedPackagePaths` | On-disk paths for each `Octopus.Action.Package.PackageReferences` entry, keyed by `Name`. |

Return `true` for success, `false` for a handled failure (with a log line
explaining why). Throw for unhandled errors — the agent catches and surfaces
`ex.Message` to the deployment log.

## The UI schema

`ui-schema.json` lives under `ui/` in the zip and drives the editor's form
for this step type. Schema vocabulary:

```jsonc
{
  "id": "mycompany.deploy-s3",        // same as the manifest's id
  "title": "Deploy to S3",
  "version": "1.0.0",                  // bump when the schema changes
  "properties": {
    "Octopus.Action.S3.BucketName": {
      "type": "string",
      "widget": "text",                // text | textarea | sensitive | select | checkbox | package-ref
      "label": "Bucket name",
      "required": true,
      "helpText": "S3 bucket to upload to."
    },
    "Octopus.Action.S3.Acl": {
      "type": "string",
      "widget": "select",
      "label": "ACL",
      "default": "private",
      "enum": [
        { "value": "private",      "label": "Private" },
        { "value": "public-read",  "label": "Public read" }
      ]
    }
  }
}
```

The editor (`SchemaDrivenStepFormDialog`) renders one field per property,
applies validation, and writes the values into the step's `Config` bag using
the property key. Your handler reads them via `context.Step.Config[key]`.

Schema changes between versions: the editor handles the diff for you
([D-7.2](../TASKS.md)) — when the user switches from v1.0.0 to v1.1.0, fields
that exist in both versions carry over, added fields get the new default,
and dropped fields toast a warning. Bump `version` in `ui-schema.json` for
every breaking schema change.

## Signing setup

KrakenDeploy verifies every package against a configured RSA public key
before installing it. The signing recipe (`StepPackageSigner` in
`Kraken.SDK`):

```text
input  = UTF-8(JSON(manifest with signature blanked))  ||  SHA-256(executor.dll)
sig    = base64( RSA-SHA256-sign( input, project-private-key ) )
manifest.signature = sig
```

Both the manifest metadata AND the executor DLL bytes are subject to
verification — an attacker can't swap the DLL while keeping the signed
manifest, and can't swap the manifest while keeping the DLL.

### Generate a signing key

```pwsh
# Private key — keep secret, never commit. Use a hardware token or
# CI secret store for the production signing identity.
openssl genrsa -out kraken-signing.key 4096

# Matching public key — distribute to every Kraken server that should trust
# packages signed by this key.
openssl rsa -in kraken-signing.key -pubout -out kraken-signing.pub
```

### Sign your package — the easy path

The `kraken pack` CLI verb builds (if needed) and signs in one step:

```pwsh
# 1. Build only (dev sentinel signature — works locally with AllowUnsignedUploads)
kraken pack ./MyCompany.MyStep/MyCompany.MyStep.csproj

# 2. Build + sign for production
kraken pack ./MyCompany.MyStep/MyCompany.MyStep.csproj `
            --key ./kraken-signing.key                 `
            --output ./out/mycompany.deploy-s3-1.0.0.kdeploy-step
```

Modes (dispatched by extension):

| Input | Behaviour |
|---|---|
| `.csproj` | Runs `dotnet build -c Release`, locates the produced `.kdeploy-step`, optionally signs it. |
| `.kdeploy-step` | Skips the build and just re-signs the existing archive. Useful in CI when a previous job built the zip. |

Without `--key`, the dev sentinel signature emitted by `KrakenStepPackage.targets`
stays in place — fine for local iteration with `AllowUnsignedUploads = true`, **never**
for production.

### Sign your package — the manual path

If you can't invoke the CLI (constrained CI image, custom build host), the same
recipe lives behind `Kraken.SDK`'s `StepPackageSigner`:

```csharp
using System.IO.Compression;
using KrakenDeploy.Contracts.StepPackages;

var archivePath  = "bin/Debug/net10.0/mycompany.deploy-s3-1.0.0.kdeploy-step";
var privateKey   = File.ReadAllText("kraken-signing.key");
using var rsa    = StepPackageSigner.ImportPrivateKeyFromPem(privateKey);

using var fs   = File.Open(archivePath, FileMode.Open, FileAccess.ReadWrite);
using var zip  = new ZipArchive(fs, ZipArchiveMode.Update);
var manifestEntry = zip.GetEntry("manifest.json")!;
var manifest      = StepPackageManifestJson.Deserialize(
    new StreamReader(manifestEntry.Open()).ReadToEnd());

var executorEntry = zip.GetEntry($"executor/{manifest.ExecutorAssembly}")!;
var tempDll       = Path.GetTempFileName();
using (var src = executorEntry.Open())
using (var dst = File.Create(tempDll)) { src.CopyTo(dst); }

var signed = StepPackageSigner.Sign(manifest, tempDll, rsa);

manifestEntry.Delete();
var newEntry = zip.CreateEntry("manifest.json");
using (var w = new StreamWriter(newEntry.Open()))
{
    w.Write(StepPackageManifestJson.Serialize(signed));
}
File.Delete(tempDll);
```

`kraken pack` runs exactly this code path under the hood (see
[`PackCommands.SignArchive`](../src/KrakenDeploy.Cli/Commands/PackCommands.cs)).

### Server-side trust

On every Kraken server that should trust packages from your key:

```jsonc
// appsettings.json
{
  "StepPackages": {
    "TrustedPublicKey": "/etc/kraken/signing-keys/mycompany.pub",
    // OR inline:
    // "TrustedPublicKey": "-----BEGIN PUBLIC KEY-----\nMI...\n-----END PUBLIC KEY-----"
    "AllowUnsignedUploads": false   // production default
  }
}
```

The agent reads the same `StepPackages:TrustedPublicKey` setting to verify
on-disk packages before loading them. Configure it the same way on every
agent host.

### Dev mode

While iterating locally, skip signing:

```jsonc
{
  "StepPackages": {
    "AllowUnsignedUploads": true,   // server: accept missing / sentinel signatures
    "AllowUnsignedLoads":   true    // agent:  load missing / sentinel signatures
  }
}
```

The MSBuild pack target emits `"signature": "unsigned-dev-build"` by default;
both flags treat that sentinel as "no signature" and let the package through
with a warning log line.

**Never turn these on in production** — they defeat the entire trust model.

## Local testing

1. Build → either `dotnet build` (dev sentinel signature) or
   `kraken pack ./MyStep.csproj --key ./kraken-signing.key` (real signature).
2. Upload via the UI: `/step-packages` → Upload → pick the `.kdeploy-step`.
3. Or via REST:

   ```pwsh
   curl -X POST `
        -H "Authorization: Bearer $env:KRAKEN_TOKEN" `
        -F "file=@bin/Debug/net10.0/mycompany.deploy-s3-1.0.0.kdeploy-step" `
        https://kraken.local/api/step-packages
   ```

4. Verify with `GET /api/step-packages?name=mycompany.deploy-s3` —
   should show your new install.
5. Add the step to a project's process via the editor: pick "Deploy to S3"
   from the step-type picker. The version dropdown shows your package's
   version; on each subsequent build you can `dotnet build` → upload → bump.

## Publishing via the GitHub catalog feed

KrakenDeploy installations can pull packages from
[`KrakenDeploy/StepPackages`](https://github.com/KrakenDeploy/StepPackages) (or
any GitHub repo configured under `StepPackages:Catalog:Owner` / `:Repo`).
The hourly Hangfire job `kraken.step-package-catalog-poll` scrapes
`GET /repos/{owner}/{repo}/releases?per_page=100` and persists discovered
entries. Admins see them under `/step-packages` → Catalog tab.

For your package to be discoverable, each GitHub Release must:

1. Attach the `.kdeploy-step` file as a release asset.
2. Embed the manifest in the release notes as a fenced JSON block:
   ````markdown
   ```json
   {"id":"mycompany.deploy-s3","version":"1.0.0", ... }
   ```
   ````
3. Include the archive's SHA-256, either as a fenced ` ```sha256 ``` ` block
   or as a single-line `SHA-256: <hex>` directive in the body.
4. **Not** be marked as a draft or pre-release.

A minimal `release-notes.md` template:

````markdown
## What's new

- Initial public release.

## Manifest

```json
{ ...the contents of manifest.json from inside the .kdeploy-step zip... }
```

## SHA-256

```sha256
0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
```
````

Compute the archive SHA-256:

```pwsh
# PowerShell on Windows
Get-FileHash bin/Debug/net10.0/mycompany.deploy-s3-1.0.0.kdeploy-step -Algorithm SHA256
```

```bash
# bash on macOS / Linux
sha256sum bin/Debug/net10.0/mycompany.deploy-s3-1.0.0.kdeploy-step
```

A GitHub Actions workflow that builds + signs + releases for every git tag
push lives in the
[`KrakenDeploy/StepPackages` repository's `.github/workflows/release.yml`](https://github.com/KrakenDeploy/StepPackages)
(reference implementation; copy into your own publishing repo).

## Reference: stable SDK surface

`Kraken.SDK` exposes a narrow stable surface. SemVer applies — MAJOR bumps
break the ABI, MINOR adds new types or members with sensible defaults,
PATCH is bugfix-only.

| Namespace | Type | Purpose |
|---|---|---|
| `KrakenDeploy.Contracts.Steps` | `IStepHandler` | The contract every step type implements. |
| | `StepHandlerContext` | What handlers receive on each call. |
| | `StepUiSchema*` | Schema vocabulary the editor renders. |
| `KrakenDeploy.Contracts.StepPackages` | `StepPackageManifest` | Manifest record. |
| | `StepPackageManifestJson` | (De)serialise + canonical-signature-input. |
| | `StepPackageFiles` | Canonical zip-layout filenames. |
| | `StepPackageSigner` | RSA-SHA256 sign + verify. |
| `KrakenDeploy.Contracts` | `DeploymentPlan` / `DeploymentStepPlan` | Wire contract sent to the agent. |
| | `PackageReference` | Octopus-compatible referenced-package shape. |

What's NOT in `Kraken.SDK`:

- Anything under `KrakenDeploy.Server.*` (server-only — DB, REST, UI).
- Anything under `KrakenDeploy.Agent.*` (agent-only — `StepPackageLoader`,
  transport, etc.).
- Internal helpers like `ScriptRunner` (lives in `KrakenDeploy.Steps.Common`,
  shared across the in-repo Steps.* projects but not part of the public SDK).

Cross-project boundaries to be aware of: when the agent loads your handler,
the `StepPackageAssemblyLoadContext` delegates `KrakenDeploy.Contracts.*`
back to the agent's default load context — so `IStepHandler` in your DLL
**is the same type** as the agent's `IStepHandler`. Type-identity holds.

## Reference example: AWS S3 upload

[`examples/AwsS3UploadStepPackage`](../examples/AwsS3UploadStepPackage/)
is a non-trivial sample demonstrating the patterns this guide teaches.
The sample bundles `AWSSDK.S3` v4 and **works against real S3 out of the
box** — `dotnet build` + `kraken pack` produces a working
`.kdeploy-step` that talks to `Amazon.S3.AmazonS3Client`.

| Pattern | Where in the example |
|---|---|
| Async I/O end-to-end | `AwsS3UploadStepHandler.HandleAsync` |
| Live log streaming | `context.LogAsync("info", "Uploaded …")` between files |
| Artifacts directory | `WriteArtifactManifestAsync` drops `uploaded.json` into `ArtifactsDir` |
| Cancellation honored | `ct.ThrowIfCancellationRequested()` between files; `OperationCanceledException` rethrown |
| Config validation | `TryParseConfig` fails loudly on missing required keys + asymmetric credentials |
| Test seam without DI | `internal` ctor taking `Func<S3UploadConfig, IS3Uploader>` + `[InternalsVisibleTo]` |
| Sensitive variables | UI schema marks `SecretAccessKey` as `sensitive: true` + `widget: "variable"` |
| Real third-party SDK packaging | `<CopyLocalLockFileAssemblies>true</CopyLocalLockFileAssemblies>` ships `AWSSDK.S3.dll` + `AWSSDK.Core.dll` inside `executor/` |
| Disposable resources | `IS3Uploader : IAsyncDisposable` + `await using` in the handler; `AmazonS3Client.Dispose()` runs at end-of-step |

Credential handling: both `AccessKeyId` + `SecretAccessKey` set →
`BasicAWSCredentials`; both blank → SDK's default chain (env vars / IAM
role); only one set → hard config error. See
[the sample's README](../examples/AwsS3UploadStepPackage/README.md) for
the full walk-through.

### Bundling third-party DLLs in your step package

If your step package uses any NuGet runtime dependency the agent
doesn't already host (anything beyond `Octostache` + the gRPC + protobuf
stack — those happen to be Agent transitives), you need
`<CopyLocalLockFileAssemblies>true</CopyLocalLockFileAssemblies>` in
your `.csproj`. Class libraries don't copy NuGet runtime DLLs to
`bin/$(Configuration)/$(TargetFramework)/` by default, and the
`KrakenStepPackage.targets` pack target globs that directory for
DLLs to ship in `executor/`. Without the flag your archive's
`executor/` will only carry your project's own DLL — and the agent's
`AssemblyDependencyResolver` will fail to resolve the third-party type
at handler-load time.
